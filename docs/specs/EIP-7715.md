# EIP-7715 — Wallet Execution Permissions

**Status**: Draft
**Created**: 2024-05-24
**Requires**: EIP-4337, EIP-7710
**Source**: https://eips.ethereum.org/EIPS/eip-7715
**Last checked**: 2026-04-29

## TL;DR

JSON-RPC method that lets a DApp request permissions from a wallet to execute transactions on the user's behalf — debit-style. Wallet returns a `context` blob the DApp later redeems via the ERC-7710 `DelegationManager.redeemDelegations()`. Solves: subscription/recurring/agent flows where signing every tx is friction.

## Core Method

```typescript
wallet_requestExecutionPermissions(params: PermissionRequest[])
  : Promise<PermissionResponse[]>
```

## Types (verbatim)

```typescript
type PermissionRequest = {
  chainId: Hex;
  from?: Address;
  to: Address;
  permission: {
    type: string;                    // e.g. "native-token-allowance"
    isAdjustmentAllowed: boolean;
    data: Record<string, any>;
  };
  rules?: {
    type: string;                    // e.g. "expiry"
    data: Record<string, any>;
  }[];
};

type PermissionResponse = PermissionRequest & {
  context: Hex;                      // opaque blob redeemed via 7710
  dependencies: {
    factory: `0x${string}`;          // ERC-4337 account factory
    factoryData: `0x${string}`;
  }[];
  delegationManager: `0x${string}`;  // ERC-7710 contract address
};

type ExpiryRule = {
  type: "expiry";
  data: { timestamp: number };       // unix seconds
};
```

## Companion JSON-RPC Methods

```typescript
wallet_revokeExecutionPermission({ permissionContext: Hex })
wallet_getSupportedExecutionPermissions(): Record<
  "permission-type",
  { chainIds: Hex[]; ruleTypes: string[] }
>
wallet_getGrantedExecutionPermissions(): PermissionResponse[]
```

## State Machine

```
1. discover         DApp calls getSupportedExecutionPermissions
2. request          DApp calls requestExecutionPermissions
3. approval         Wallet shows scope to user; user approves
4. response         Wallet returns context + delegationManager
5. deploy (opt)     DApp uses factory/factoryData to deploy account
6. redeem           DApp calls delegationManager.redeemDelegations(
                      [context], [mode], [executionCallData])
```

## Execution Struct (from ERC-7710)

```solidity
struct Execution {
    address target;
    uint256 value;
    bytes callData;
}
```

## Permission Types

The spec defines **only one example**: `native-token-allowance`. Custom permission types are valid as long as wallet + DApp agree on schema. We define our own:

- `inft-spend-cap` (per-iNFT, per-epoch USDC cap, target = FeeSplitter or Base Sepolia USDC)
- `audit-job-budget` (single-use, target = oracle.zhgg.eth, expiry = 1h)

## Security Considerations (verbatim)

- **Limited Permission Scope**: "DApps should only request the permissions they need, with a reasonable expiration time"
- **Wallet Enforcement**: "Wallets MUST correctly enforce permissions"
- **User Trust**: "Users must trust that their wallet software is implemented correctly"
- **Phishing Risk**: "Malicious DApps could pose as legitimate applications and trick users into granting broad permissions"
- **Display**: "Wallets MUST clearly display the permissions to users and warn them against granting dangerous permissions"

## How zhgg Uses It

- iNFT owner (the human) grants the iNFT a `inft-spend-cap` permission via 7715
- Permission constrains: max USDC per epoch, target = our FeeSplitter or Base Sepolia USDC, expiry
- iNFT-controlled smart account (ERC-4337) holds the redemption authority
- When `audit.zhgg.eth` pays `oracle.zhgg.eth`, it calls `delegationManager.redeemDelegations()` with the cached context
- Cap exceeded → redeem fails closed, agent operation halts gracefully
- Owner revokes via `wallet_revokeExecutionPermission` if compromised

## Backwards Compatibility

Wallets without 7715 support SHOULD return an error if the JSON-RPC method is called.
