## TL;DR

Standard interface for a contract to delegate capabilities to another contract or EOA via a `DelegationManager`. The companion of ERC-7715 — 7715 grants permissions, 7710 redeems them on-chain.

## The Only Required Interface (verbatim)

```solidity
pragma solidity 0.8.23;

interface ERC7710Manager {
    /**
     * @notice Validates permission contexts and executes if caller has authority.
     * @param _permissionContexts the data used to validate the authority
     *        given to execute the corresponding execution.
     * @param _action the action to be executed (mode encoded per ERC-7579)
     * @param _modes the array of modes to execute the related executioncallData
     * @param _executionCallDatas the array of encoded executions to be executed
     */
    function redeemDelegations(
        bytes[] calldata _permissionContexts,
        bytes32[] calldata _modes,
        bytes[] calldata _executionCallData
    ) external;
}
```

That's it. The spec deliberately leaves these out of scope:
- The Delegation struct
- The granting flow (use ERC-7715 for that)
- Caveat / scope enforcement (implementation-defined)
- Revocation mechanism

## Execution Encoding (from ERC-7579)

`mode` encodes execution behavior. `executionCallData` typically includes at minimum:

```solidity
struct Execution {
    address target;
    uint256 value;
    bytes callData;
}
```

Atomicity rule: "Each tuple represents a single delegation redemption with its associated permission context, execution mode, and execution data. **Implementations MUST enforce atomicity of the batch.**"

## State Machine

```
[off-chain]   grant         (mechanism out of scope; typically ERC-7715)
              ↓
[on-chain]    redeemDelegations(permissionContexts, modes, callData)
              ↓
              DelegationManager validates each context
              ↓
              Each Execution fires, atomically as a batch
              ↓
              All-or-nothing — one failure reverts all

[off-chain]   revoke        (mechanism out of scope)
```

## Permission Context

The `bytes[]` `_permissionContexts` parameter is opaque — its structure is determined by the specific DelegationManager implementation. MetaMask's reference impl uses EIP-712 signed delegations with optional caveats (allowed-target, allowed-method, max-spend, expiry, etc.).

## Security Considerations (verbatim)

- **Audit**: "Applications implementing this interface should undergo thorough security audits"
- **Verify before redeem**: dApps "SHOULD verify permissions before attempting to execute actions by: (1) Simulating the `redeemDelegations` call (2) Using simulation results to determine if it would succeed (3) If simulation fails, request new or updated permissions"
- **No persistence assumption**: "dApps MUST NOT assume that having received a delegation in the past guarantees future execution rights"
- **Revocation risk**: "Delegations can be revoked, expire, or become invalid due to state changes"
- **Pre-flight strategy**: "Always simulate delegation redemptions before submitting them on-chain. Handle simulation failures gracefully. Consider implementing retry logic with escalating permission requests."

## How zhgg Uses It

- We deploy a **single** DelegationManager that the iNFT trusts
- iNFT owner grants via 7715 (off-chain) → wallet returns `context`
- When agent runs a job (audit pays oracle), agent calls `delegationManager.redeemDelegations()` directly
- Manager checks: caveat allows this target? Within spend cap? Not expired? Not revoked? → executes
- Single batch: pay oracle (Base Sepolia USDC) + post receipt (0G chain) — atomic across an internal cross-chain coordinator (NOT atomic across actual chains; cross-chain atomicity is out of scope)

## Cross-Chain Caveat

The `Execution.target` lives on a single chain. Our Pattern D (x402 on Base Sepolia + iNFT on 0G) means we need TWO DelegationManagers, one per chain — or a single manager on Base Sepolia with the cross-chain receipt posted via separate viem call after settlement. Pick the latter for D1 simplicity.
