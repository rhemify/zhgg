# EIP-3009 — Transfer With Authorization

**Status:** Final
**Source:** https://eips.ethereum.org/EIPS/eip-3009
**Authors:** Centre/Circle USDC team
**Last researched:** 2026-05-01

## Verdict for zhgg: **NO — keep using transitively via x402 + KeeperHub**

Direct EIP-3009 integration is a maintenance tax that buys zhgg no capability the
existing primitives (`SpendCap`, ERC-7710, x402) don't already cover. The only 3009-shaped
intent — "pay USDC for a metered service" — already works through `@keeperhub/wallet`.
Self-signing 3009 buys nothing and asset-locks us to USDC-family stablecoins.

## What it does

EIP-3009 defines three EIP-712 typed-data messages that token contracts can accept in
lieu of `transferFrom`, plus one query function. Authored by Centre for USDC; reused by
PYUSD, EURC, USDP. **Notably DAI and USDT do NOT support 3009.**

### Three typed-data messages

**`TransferWithAuthorization`** — anyone holding the signature can call the function
once `block.timestamp` is in `[validAfter, validBefore]`. Any address can submit.
```
TransferWithAuthorization(
  address from, address to, uint256 value,
  uint256 validAfter, uint256 validBefore, bytes32 nonce
)
```

**`ReceiveWithAuthorization`** — identical fields, but on-chain function adds
`require(msg.sender == to)`. Blocks front-running of single-use payment intents: a third
party who scrapes the signed payload from the mempool cannot relay it on their own
behalf.

**`CancelAuthorization`** — pre-emptively burn a specific `(authorizer, nonce)` pair
before redemption.
```
CancelAuthorization(address authorizer, bytes32 nonce)
```

**View** — `authorizationState(address authorizer, bytes32 nonce) returns (bool)`.

### Critical replay invariants (Spec §"Unique Random Nonce")

The nonce is an arbitrary, signer-chosen `bytes32` — **not sequential**. The pair
`(authorizer, nonce)` is consumed atomically on first redemption (or on cancel).
Critical contrast with EIP-2612 permit (sequential `nonces[owner]++`): EIP-3009 lets a
signer issue many concurrent authorizations without ordering, ideal for parallel intent
fulfillment.

### Domain separator footgun

`EIP712Domain(string name, string version, uint256 chainId, address verifyingContract)`.

USDC on Base mainnet uses `name: "USD Coin"` `version: "2"`, but the testnet mock USDC
at `0x036CbD53842c5426634e7929541eC2318f3dCF7e` (Base Sepolia) uses `name: "USDC"`
`version: "2"`. **That mismatch is the single most common source of "isValid: false"
from facilitators.**

## Where zhgg actually touches EIP-3009 today

The honest picture from reading every file that mentions 3009:

- **`packages/workflow/src/x402.ts`** (290 LOC) is a clean v2 facilitator client — it
  builds `paymentRequirements` and POSTs `{paymentPayload, paymentRequirements}` to
  `/verify` and `/settle`. **It treats the EIP-3009 authorization as an opaque base64
  blob; it never constructs the typed data or signs it.**
- **`apps/demo/src/keeperhub-marketplace.ts:28-104`** calls
  `createPaymentSigner({ walletLoader }).fetch(url)` from `@keeperhub/wallet@0.1.8`.
  Actual ECDSA signing happens server-side at KH against a Turnkey sub-org. The
  `hmacSecret` is just an HMAC for KH's signing endpoint — **we never hold the EVM key,
  never construct the EIP-3009 typed data, never call `eth_signTypedData_v4`**.
- **`apps/demo/src/live-deps.ts:159-214`** is the only "live" settlement path actually
  wired into `cross-agent.ts`. The non-KH branch JIT-approves USDC and calls
  `FeeSplitter.splitERC20()` directly — **regular `transferFrom` flow with standing
  approval, not 3009 at all.**
- **`packages/workflow/src/x402.ts`** is exercised by tests but not wired into the
  orchestrator. So the zhgg-authored x402 module is dead in production.

**Net:** zhgg's 3009 exposure is entirely transitive through `@keeperhub/wallet`. We
never sign, verify, or cancel an authorization ourselves.

## EIP-3009 vs alternatives for intent-driven flows

| Capability | EIP-2612 permit | **EIP-3009** | ERC-7715 (SpendCap) | ERC-7710 delegations |
|---|---|---|---|---|
| Off-chain sig, no pre-approval | Yes (sequential nonce) | **Yes (arbitrary nonce)** | No (on-chain grant tx) | Yes (off-chain) |
| Concurrent intents from same signer | No (nonce ordering) | **Yes** | Yes | Yes |
| Time window per intent | `deadline` only | **`validAfter`+`validBefore`** | period buckets | per-caveat |
| Atomic single-shot transfer | No (permit + transferFrom) | **Yes (one tx)** | No (caller pulls) | Multi-step |
| Front-run defense for execution | No | **Yes (`Receive…`)** | N/A | via redemption logic |
| User can cancel before use | overwrite nonce | **`cancelAuthorization`** | `revoke` (on-chain tx) | revoke caveat |
| Asset coverage | most ERC-20 with permit | USDC/PYUSD/EURC family **only** | any ERC-20 | any |
| Signing-cost UX | 1 sig + 1 tx | **1 sig** | 1 grant tx upfront | 1 sig |

**Where EIP-3009 wins decisively:** single-shot, time-bounded, USDC-denominated payments
where the user wants to sign once and walk away. The *only* mechanism that gives all four
of (no pre-approval, parallel nonces, validBefore window, single-tx settlement) in one
primitive. **Exactly the x402 use case.**

**Where 3009 loses to SpendCap (`contracts/src/SpendCap.sol`):** rolling budgets ("50
USDC/day for 7 days"), multi-asset caps, protocol-agnostic spend. For intents like
*"delegate 50 USDC/day to this audit agent"*, SpendCap is the right primitive; 3009 would
force you to sign 7 separate authorizations or one large authorization with no period
semantics.

**Where 3009 loses to ERC-7710:** when the agent must call arbitrary contracts ("swap
100 USDC to ETH at 0.5% slippage" — 3009 only moves the USDC, it doesn't authorize the
swap call). 3009 is for *moving stablecoins*, not for *executing arbitrary actions*.

## Mapping to the planned 18-intent palace (from CLAUDE.md)

- **`simple_swap`, `swap_with_slippage`, `send_token`** — primary action is *call the DEX
  router / call ERC-20 transfer*. 3009 only helps if paid in USDC into a meta-tx relayer;
  otherwise irrelevant.
- **`check_balance`, `check_portfolio`** — read-only, no payment.
- **`limit_swap`, `stop_loss`, `take_profit`** — solver triggers an action; 3009 cannot
  fund the arbitrary swap. ERC-7710 + SpendCap fit better.
- **`recurring_swap`, `price_alert`, `rebalance`, `add_liquidity`, `remove_liquidity`,
  `collect_fees`, `claim_airdrop`, `rebalance_full`, `range_reposition`,
  `collect_and_reinvest`** — same story: action-execution, not stablecoin transfer.
  SpendCap caps the budget; ERC-7710 authorizes the call.
- **"Buy this oracle feed for 24h, paying X USDC up front"** — *is* a 3009 sweet spot,
  and it's what x402 already does. **We already cover it transitively.**

For the 18 declared intents, only the x402-style "pay USDC for a service" lane benefits
from 3009 — and that lane already works through KH.

## Risks if we pull 3009 in directly

- **Domain-separator footguns**: USDC's `name`/`version` differs across
  mainnet/testnet/forks. Hand-rolled signers must be parameterized per deployment.
- **Asset coverage**: 3009 only works for USDC/PYUSD/EURC. The moment a user wants to
  pay in DAI, USDT, or any other ERC-20, you fall back to permit or `transferFrom`.
  Building a "first-class 3009 helper" creates a code path that breaks for half of
  plausible assets.
- **Cross-chain replay**: mitigated by `chainId` in the domain separator, but only if
  correctly populated. Mistakes here are CVE-2020-style replay bugs.
- **Operating a facilitator**: gas-relay, mempool monitoring, retry on revert, nonce
  tracking by `authorizationState`, abuse-resistance. Materially equivalent to running a
  meta-tx infra service. Cost: at least one engineer-month + ongoing ops. The free
  `https://x402.org/facilitator` is fine for testnet; production needs either Coinbase's
  paid facilitator or self-hosted.

## What to clean up instead — three concrete edits

1. **`packages/workflow/src/x402.ts:1-18`** — update header comment to be explicit that
   this module is the *server-side* gate (we ACCEPT 3009-signed payments), not a signer.
   State that no zhgg code ever constructs an EIP-3009 authorization; that responsibility
   belongs to the client (`@keeperhub/wallet`, x402 browser SDKs, or any future
   viem-native client we add).
2. **`README.md`** — the line "x402: EIP-3009 USDC payments on Base Sepolia" is
   technically true but misleading: it implies we sign 3009. Reword to "x402 facilitator
   client; EIP-3009 signing handled client-side by `@keeperhub/wallet` (KH-custodied
   Turnkey)."
3. **Add `packages/sdk/intents/_types.ts` rail enum** — when the intent palace lands,
   model the payment rail as `{ rail: 'x402' | 'spendcap' | 'erc7710' | 'direct' }` and
   route `pay_for_oracle`-style intents to `x402` (delegating signing to the configured
   payment client) and budget/action intents to `spendcap`/`erc7710`. Makes the
   architectural choice load-bearing in code rather than implicit.

## If we ever DO reverse this call

(Triggers: KH dependency becomes a problem, OR we want to monetize a self-hosted
facilitator.)

Build-first checklist:
1. `packages/workflow/src/eip3009.ts` with a viem `signTypedData` helper parameterized
   by per-asset domain (USDC mainnet vs Sepolia mock vs PYUSD).
2. Tiny facilitator at `apps/facilitator/` that calls `transferWithAuthorization` and
   tracks `authorizationState`.
3. `cancelAuthorization` UX surface in the TUI for users to abort pending intents.

**None of that is needed for the P0 intent slice in `CLAUDE.md`.**

## Bottom line

Stick with x402 + KeeperHub for stablecoin payments and lean on `SpendCap` + ERC-7710
for the intent + solver expansion. Direct EIP-3009 integration buys zhgg no capability
the existing primitives don't already cover.
