# EIP-8021 — Transaction Attribution via Calldata Suffix

## Status
- Draft (ERC, not yet Final). Authored by Conner Swenberg (`@ilikesymmetry`).
- Created: September 2025. Tracked at `https://www.erc8021.com/` and the ERCs repo.
- Adopted in production by Base (Builder Codes), `ox` library, Celo demo, and several wallets/aggregators.

> SCOPE DISCREPANCY (read this): ERC-8021 is **NOT** a fee-splitting standard. It does not define a splitter contract, recipient list, or on-chain value distribution. It is a **read-only attribution tag** appended to calldata that off-chain indexers (and protocols that opt in) use to identify which app/wallet/service facilitated a transaction. Any "fee split" — including zhgg's 4-way cut — must be implemented as a **separate splitter contract** (or off-chain routing layer like x402) that *reads* 8021 codes and decides what to pay whom. The cheat sheet below reflects the actual EIP, then describes how zhgg layers a splitter on top.

## TL;DR
ERC-8021 appends a fixed-trailing suffix to any transaction's calldata so off-chain systems can attribute the tx to one or more entity codes (e.g., `baseapp`, `privy`). Smart contracts ignore the trailing bytes (EVM allows excess calldata), so it works on any existing contract with no ABI change, no proxy upgrade, no redeployment. It benefits builders/wallets/aggregators who want measurable, programmatic credit for the volume they route.

## Core Mechanism
- Append a self-describing suffix to the **end** of `tx.data`.
- Recipient contract ignores the trailing bytes; selector + args still decode correctly.
- Suffix is parsed **backwards from end of calldata**: marker (16B) → schemaId (1B) → schema body.
- No callback, no extra tx, no signature — pure passive metadata.

## Suffix Schema (verbatim layout)

Magic marker (last 16 bytes of every 8021 suffix):
```
0x80218021802180218021802180218021
```

Schema 0 — Canonical Registry (most common):
```
[codesLength: 1 byte][codes: ASCII, comma-delimited][schemaId: 0x00][marker: 16 bytes]
```
Example for code `celo` (ASCII `0x63656c6f`, 4 bytes):
```
0x 04 63656c6f 00 80218021802180218021802180218021
   ^  ^        ^  ^
   |  ASCII    schemaId=0
   length(4)              marker (16B)
```

Schema 1 — Custom Registry: same as Schema 0 plus `(address: 20B, chainId: uint)` for an off-chain registry contract resolving codes; `schemaId = 0x01`.

Schema 2 — CBOR-Encoded: extensible CBOR map with optional `appCode`, `walletCode`, `serviceCodes[]`, `registries`, arbitrary `metadata`; `schemaId = 0x02`.

## Attribution Type (verbatim from `ox` reference impl)
```ts
// Schema 0
type AttributionSchemaId0 = { codes: readonly string[]; id?: 0 }
// Schema 1
type AttributionSchemaId1 = {
  codes: readonly string[]
  codeRegistry: { address: Address; chainId: number }
  id?: 1
}
// Schema 2
type AttributionSchemaId2 = {
  appCode?: string
  walletCode?: string
  serviceCodes?: readonly string[]
  registries?: { app?: {...}; wallet?: {...} }
  metadata?: Record<string, unknown>
  id?: 2
}
export const ercSuffix = '0x80218021802180218021802180218021'
```

## State Machine
1. dApp builds tx normally → selector + args.
2. SDK (`ox.Attribution.toDataSuffix(...)`) computes suffix bytes.
3. Wallet sends `tx.data = encodedCall || suffix`.
4. Target contract executes — extra trailing bytes are ignored by ABI decode.
5. Off-chain indexer reads `tx.input`, slices last 16 bytes, checks marker, decodes schema, attributes.

## "Splitter" — NOT Part of ERC-8021
The EIP defines no `IFeeSplitter`. To split fees you write your own contract that on entry reads `msg.data[msg.data.length-16:]`, verifies the marker, decodes codes, and routes value. There is no canonical splitter interface from the EIP. Reference impls (`ox`, Base SDK) are pure off-chain decoders.

## Calldata Encoding Example
Self-transfer of 1 wei tagged `celo`:
```
to:    0x...self
value: 1
data:  0x0463656c6f0080218021802180218021802180218021
```
Real swap: `data = swapSelector || encodedArgs || 0x0463656c6f00<marker>`.

## Off-chain Indexing
Detection rule: `RIGHT(tx.input, 16) == 0x80218021802180218021802180218021`.
Dune SQL example:
```sql
SELECT block_time, hash, "from", "to", value
FROM ethereum.transactions
WHERE RIGHT(BYTEARRAY_TO_HEX(data), 32) = '80218021802180218021802180218021'
```
No event emission is required by the EIP — attribution is purely calldata-based. Subgraphs detect by tx-input filter; downstream payment (e.g., x402) routes micropayments to attributed entities post-hoc.

## Security Considerations
- **No replay protection needed** — suffix is part of signed tx data; any modification invalidates the signature.
- **No execution risk** — bytes are inert; recipient ignores them. ABI decoders MUST tolerate trailing data (most do).
- **Code spoofing** — codes are unauthenticated strings; canonical registry (Schema 0) or signed registry (Schema 1) gates which codes are "real". Off-chain indexers MUST resolve via the registry, not trust raw bytes.
- **Calldata gas** — each suffix byte costs 4 gas (zero) / 16 gas (non-zero). Schema 0 with one code ≈ ~22 bytes ≈ ~350 gas. Negligible vs swap gas, non-trivial on L1 for high-frequency txs.
- **Privacy** — codes are public; treat as observable telemetry.
- **Contract incompatibility** — a tiny minority of contracts revert on excess calldata (strict ABI decoders, some custom assembly). Test target before adopting.
- **Multi-call ambiguity** — only the outer tx carries the suffix; inner calls don't inherit. Aggregators must carry attribution at the top level.

## Deployment Status
- **No on-chain contracts required by the EIP.** Pure calldata convention.
- Reference SDK: `ox` library — `import { Attribution } from 'ox/erc8021'` (`wevm/ox`).
- Live integrations: Base Builder Codes, Privy, Celo (demo), Phantom, Arcadia, multiple ETHDenver 2026 projects.
- Indexers: Dune (any chain with tx data), custom subgraphs.

## How zhgg Uses It
- **8021 = the tag, not the wallet.** Append a Schema 2 suffix on every audit-receipt-paying tx with `appCode='zhgg'`, `walletCode=<user wallet code>`, `serviceCodes=['keeperhub', '<agent-owner-id>']`.
- **Splitter sits on top.** `contracts/src/FeeSplitter.sol` (zhgg-owned, not part of EIP) reads the 8021 suffix in its receive/fallback, decodes codes, and routes per zhgg's 4-way policy:
  - 85% → agent owner (workflow creator — like Phantom's Hyperliquid app cut, drives open onboarding)
  - 5% → KeeperHub (execution infra subsidy)
  - 5% → zhgg treasury (protocol)
  - 5% → reputation commons (public goods pool that backs the agent reputation graph)
  Rationale: bulk to creators because supply-side (intent authors) is the scarce resource; protocol/infra/commons each take a flat 5% so the split is legible and fair.
- **0G Storage Log audit trail.** Indexer normalises `(txHash, codes, recipients, amounts)` into NDJSON and pins to 0G; the audit page replays from log, not chain RPC.
- **No new ABI** for tagging — suffix is appended in the SDK before signing, so any on-chain rail (Uniswap v4 swap, ENS payment) carries attribution transparently.
