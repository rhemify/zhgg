# EIP-8183 — Agentic Commerce Protocol (ACP)

**Status:** Draft (Standards Track)
**Created:** 2026-02-25
**Authors:** Davide Crapis (@dcrapis, ETH Foundation), Bryan Lim, Tay Weixiong, Chooi Zuhwa (Virtuals Protocol)
**Source:** https://eips.ethereum.org/EIPS/eip-8183
**Discussion:** https://ethereum-magicians.org/t/erc-8183-agentic-commerce/27902
**Last researched:** 2026-05-02

## Verdict for zhgg: **NO for May 6 hackathon, LATER as bolt-on**

zhgg's existing primitives (`AxiomCommit + SpendCap + AgentReceiverWallet + FeeSplitter + AgentRegistry`)
already cover every ACP concept except one: a **persistent on-chain Job state machine
with a third-party evaluator role** (someone who is neither buyer nor seller signs
"done"). That delta only matters when zhgg expands to "agent hires agent" commerce —
which is post-hackathon scope.

## What it does

A minimal **job-escrow + evaluator-attestation** primitive. Client creates a job,
optionally assigns a provider, sets a budget, and `fund()`s an ERC-20 escrow. Provider
calls `submit(jobId, deliverable)` (a `bytes32` reference). A single named **evaluator**
address — which MAY be the client itself, or a smart contract that verifies a ZK proof /
aggregates signals — alone may `complete(jobId, reason)` (releases escrow to provider,
optional fee to treasury) or `reject(jobId, reason)` (refunds client). After
`expiredAt`, anyone can call `claimRefund`.

State machine: **Open → Funded → Submitted → {Completed | Rejected | Expired}**.

Optional `IACPHook` interface (`beforeAction` / `afterAction` with selector dispatch)
for policy/reputation extensions; explicitly designed to compose with **ERC-8004
reputation** and **ERC-2771 + ERC-2612** for gasless flows. **"x402 compatibility" is
called out by name** as a primary use case.

## Core interface (load-bearing 6 functions)

```solidity
function createJob(
    address provider, address evaluator, uint256 expiredAt,
    string desc, address hook
) external returns (uint256 jobId);

function fund(uint256 jobId, uint256 expectedBudget) external;
function submit(uint256 jobId, bytes32 deliverable) external;       // provider only
function complete(uint256 jobId, bytes32 reason) external;          // evaluator only
function reject(uint256 jobId, bytes32 reason) external;            // client(Open) | evaluator(Funded/Submitted)
function claimRefund(uint256 jobId) external;                       // anyone, post-expiry
```

## Map to zhgg primitives

| ERC-8183 concept | zhgg equivalent today |
|---|---|
| Job creation + budget | x402 v2 verify/settle (off-chain payment intent) |
| Escrow on Funded | `AgentReceiverWallet` + `SpendCap` (per-permission cap pull) |
| Evaluator attests Completed | `AxiomCommit` reveal + `FeeSplitter` distribution (85/5/5/5 cut on settle = "fee on completion") |
| `reason` attestation hash | `commitHash` / `memoryRoot` already in `AxiomCommit` and `AgentNFT` |
| Reputation hook → ERC-8004 | Already integrated via `AgentRegistry.sol` |
| ERC-2771 + 2612 ("x402 compat") | Already in `packages/workflow/src/x402.ts` |

**The one delta** ACP cleanly defines that zhgg currently lacks: **a persistent on-chain
Job state machine with a third-party evaluator role**. Today zhgg's evaluator is implicit
— the user signing the x402 challenge and the AxiomCommit reveal both come from the
*same* counterparties. For agent-to-agent commerce where neither end trusts the other,
ACP's evaluator-as-contract pattern (e.g. ZK proof verifier acts as evaluator) is
genuinely useful.

## Why NO for hackathon

- Phase 16 (ERC-7710 DelegationManager) closes 12 of 18 intents — that's the actual gap
- ACP solves a different problem (multi-party commerce arbitration), not zhgg's current
  gap (intent execution + caps)
- ~250-400 LOC plus a real evaluator design, with no judges yet looking for it
- 5 days to deadline

## Why LATER (post-hackathon, ~150 LOC clean bolt-on)

When zhgg expands to "agent hires agent" (e.g. solver pays inference provider on
submission), wrap `AgentReceiverWallet` with an 8183-shaped `Job` contract:
- `complete()` callback triggers the existing `FeeSplitter`
- `reason` field stores `memoryRoot`
- evaluator = a new on-chain `EvaluatorRegistry.sol` mapping intent class → trusted
  evaluator contract

**Don't fork the reference impl yet** — it's still Draft and the interface may shift.

## Alternatives considered

None of Permit2 / Safe / Sablier / Hyperlane fit — they solve different shapes
(allowances, multisig, streaming, messaging). The closest *adopted* equivalent is
**Hats Protocol + EAS attestations** for the evaluator role, but that's heavier than
8183. If zhgg ever ships escrow, **8183 is the right shape** — just not the right time.
