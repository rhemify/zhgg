# EIP-7857 — Intelligent NFT (iNFT)

**Status**: Draft (status not explicitly stated in published EIP)
**Created**: 2025-01-02
**Requires**: not specified
**Source**: https://eips.ethereum.org/EIPS/eip-7857
**Last checked**: 2026-04-29

## TL;DR

NFT standard for AI agents where the metadata is private (encrypted off-chain) and ownership transfer requires a verifiable proof (TEE or ZKP) that re-encrypts the data for the new owner. Unlike ERC-721, the iNFT does NOT inherit ERC-721 and does NOT use `tokenURI` — it uses on-chain `dataHash` pointers + off-chain encrypted blobs + a pluggable proof verifier.

## Core Concept

```
on-chain:           IntelligentData = { dataDescription, dataHash }
off-chain:          encrypted blob keyed by sealed key (TEE-protected or ZK-proven)
transfer proof:     re-encrypt off-chain, prove on-chain via IERC7857DataVerifier
authorization:      authorizeUsage adds an address to an allow-list; data access is
                    enforced by an off-chain "Sealed Executor" (out of scope of EIP)
```

## Key Interfaces (verbatim)

### Verifier (oracle)

```solidity
enum OracleType { TEE, ZKP }

struct AccessProof {
    bytes32 oldDataHash;
    bytes32 newDataHash;
    bytes nonce;
    bytes encryptedPubKey;
    bytes proof;
}

struct OwnershipProof {
    OracleType oracleType;
    bytes32 oldDataHash;
    bytes32 newDataHash;
    bytes sealedKey;
    bytes encryptedPubKey;
    bytes nonce;
    bytes proof;
}

struct TransferValidityProof {
    AccessProof accessProof;
    OwnershipProof ownershipProof;
}

interface IERC7857DataVerifier {
    function verifyTransferValidity(
        TransferValidityProof[] calldata _proofs
    ) external returns (TransferValidityProofOutput[] memory);
}
```

## State Machine

```
mint                  → TokenData created, owner set, iDatas seeded
iTransfer(proof)      → verifier checks proof → owner changes → approvedUser cleared
                        → emits PublishedSealedKey for new owner to decrypt off-chain
iClone(proof)         → new tokenId created, encrypted blob re-encrypted for _to
authorizeUsage        → adds _user to authorizedUsers[] (does NOT grant data access)
revokeAuthorization   → removes _user
delegateAccess        → user-level off-chain access assistant pointer
```

## Authorization vs Access (Critical Gotcha)

`authorizeUsage` only emits an event and updates a list. The actual data access enforcement happens off-chain via a **Sealed Executor** — an out-of-scope component that authenticates requests against the authorized list and decrypts the data inside a trusted environment.

This means: **on-chain alone, the iNFT cannot stop unauthorized inference.** zhgg's Sealed Executor lives in 0G Compute TEE and refuses jobs whose payer is not in `authorizedUsersOf(tokenId)`.

## Royalty / ERC-8021 Integration

EIP-7857 itself does **not** define royalties. We layer royalties externally:
- Payment flow hits zhgg's `FeeSplitter` (ERC-8021 calldata suffix)
- Splitter routes 85% to `ownerOf(tokenId)`
- iNFT and royalty enforcement are decoupled — by design

## Security Considerations (verbatim from EIP)

- **Proof verification**: implementations must carefully verify all assertions; replay attacks must be prevented
- **Data privacy**: only hashes + sealed keys on-chain; actual data stored and transmitted off-chain
- **Key management**: TEE supports private-key-of-receiver flows, ZKP does not
- **Access control**: operations restricted to token owners only
- **Atomicity**: critical state changes must be atomic and verifiable
- **Sealed Executor**: out of scope, but crucial — authenticates and processes user requests

## How zhgg Uses It

- `contracts/src/AgentNFT.sol` is our iNFT implementation
- Each seed agent (`audit.zhgg.eth`, `oracle.zhgg.eth`) = one iNFT
- `IntelligentData[]` holds capability manifest hash + memory root hash + system prompt hash
- Encrypted blobs live on 0G Storage KV, keyed by `dataHash`
- Sealed Executor = our 0G Compute TEE caller, refuses unauthorized jobs
- `authorizeUsage` fires when a payer pays via x402 — adds them for the duration of the job
- Royalties via separate `FeeSplitter` (ERC-8021), not built into iNFT

## Backwards Compatibility

Does NOT inherit from ERC-721. Implementations may opt-in to dual-standard support, but EIP-7857 alone is incompatible with ERC-721 wallets/marketplaces.
