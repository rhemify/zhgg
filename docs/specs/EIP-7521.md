# EIP-7521 — General Intents for Smart Contract Wallets

**Status:** Draft (stranded — last spec update Dec 2023)
**Source:** https://eips.ethereum.org/EIPS/eip-7521
**Reference impl:** https://github.com/essential-contributions/ERC-7521 (last push 2024-04-19)
**Last researched:** 2026-05-01

## Verdict for zhgg: **NO — skip it**

zhgg's `AxiomCommit` + Zod intent registry + ERC-1271 receiver wallet + x402 already
constitute a working intent-and-solver stack. The only standard worth tracking for a
future cross-chain expansion is **ERC-7683**, not 7521.

## What it does

ERC-7521 is a generalized intent entry-point standard for smart contract wallets. It
mirrors ERC-4337's architecture but replaces "execute calldata" with "execute a list of
intent segments, each interpreted by an on-chain `IntentStandard` contract that the user
picks at sign time." Users sign a `UserIntent`, gossip it to a mempool, **solvers**
combine multiple `UserIntent`s into an `IntentSolution`, and submit it via `handleIntents`
on a singleton `EntryPoint`. Promise: wallets never need upgrades when new intent types
appear — users opt into a new `IntentStandard` contract just by signing an intent that
references its standard ID.

## Data model (verbatim from §Specification)

```solidity
struct UserIntent     { address sender; bytes[] segments; bytes signature; }
struct IntentSolution { uint256 timestamp; UserIntent[] intents; uint256[] order; }
```

The first 32 bytes of every entry in `segments` is the **standard ID** (registered
permissionlessly via `EntryPoint.registerIntentStandard`). Each registered standard
implements:

```solidity
function validateIntentSegment(bytes segmentData) external pure;
function executeIntentSegment(IntentSolution, uint256 executionIndex,
                              uint256 segmentIndex, bytes context) external returns (bytes);
```

Wallets implement `validateUserIntent(UserIntent, bytes32 hash)` and
`generalizedIntentDelegateCall(bytes data)`. The wallet gates that delegatecall by calling
back into `EntryPoint.verifyExecutingIntentSegmentForStandard` — the only safety hinge in
the whole design (§Security Considerations).

### Relation to other standards

- **ERC-4337**: same pattern (singleton EntryPoint, signature in validation phase,
  execution phase). 7521 is explicitly "4337 but for intents instead of UserOps".
- **ERC-7710 / ERC-7715**: orthogonal. Those describe *delegated permissions* (caps,
  allowances) on a wallet. 7521 describes *how an entry point dispatches signed intents
  to standard contracts*. zhgg's `SpendCap.sol` is a 7715-aligned cap manager — it would
  sit *underneath* a 7521 standard, not be replaced by one.
- **EIP-7702**: not connected. 7702 lets EOAs temporarily behave like contract wallets;
  7521 still requires the wallet to implement `validateUserIntent`.

## Adoption status

- **Status: Draft.** Created 2023-09-19, last spec update was Revision 1 in December 2023.
  File was relocated from `ethereum/EIPs` to `ethereum/ercs` (now an ERC, not a core EIP).
- **Reference impl: `essential-contributions/ERC-7521`** — 44 stars, 8 forks, last push
  2024-04-19 (~2 years stale as of today). 6 open issues, no recent merges. The Essential
  team appears to have moved on rather than pushing 7521 to Final.
- **Production usage: effectively zero.** No major wallet, paymaster, or solver network
  has shipped 7521 EntryPoint integrations. UniswapX, CoW Swap, 1inch Fusion, Across,
  Anoma — all use bespoke intent formats.
- The intent-standard space has consolidated around **ERC-7683** (cross-chain), which
  has the Open Intents Framework with Arbitrum/Optimism/Scroll/Polygon support.

## Fit with zhgg today

| 7521 concept | zhgg equivalent today | Gap? |
|---|---|---|
| `UserIntent` (signed envelope) | Canonical plan JSON committed via `AxiomCommit.commitPlan(tokenId, keccak(plan))` (`contracts/src/AxiomCommit.sol`) | 7521 standardises the on-chain shape; zhgg only stores a hash |
| `IntentSolution` ordering across multi-intent | Not present — zhgg is single-agent-per-loop | We don't need multi-intent batching today |
| `EntryPoint.handleIntents` | Off-chain orchestrator `apps/demo/src/cross-agent.ts` driving `AgentReceiverWallet.execute` | 7521 would on-chain a router we currently keep in TS |
| `IntentStandard.executeIntentSegment` | Zod intent registry described in `CLAUDE.md` (`packages/sdk/src/intents/*.ts`) | 7521's "standard" is a contract; zhgg's is a TS file plus an MCP tool |
| Solver auctions / MEV | Not present — KH marketplace 70/15/15 split is pre-priced via x402 | 7521 assumes a solver mempool exists; we don't have one |
| Wallet `validateUserIntent` | `AgentReceiverWallet.isValidSignature` (ERC-1271) | Compatible in spirit |
| Spend-cap enforcement | `SpendCap.sol` per-`permissionId` caps (ERC-7715-aligned) | Already richer than 7521 provides natively |
| Audit trail | `FeeSplitter` ERC-8021 calldata-suffix attribution + `writeAuditLog` (0G Storage Log) | 7521 has none — no audit story |

**What 7521 would add that we don't have:** (a) a *standardised* on-chain intent envelope
so third-party solvers/wallets could interop with us, and (b) a multi-intent batching
primitive (`IntentSolution.order`) for combining several agents' intents in one tx.

**What 7521 does *not* add over zhgg:** spend caps (we have 7715), reputation/identity
(8004), auditability (AxiomCommit + 0G Storage Log + 8021 attribution), payment rails
(x402/3009), TEE attestation. All shipped already.

## Hypothetical integration (NOT recommended, kept for reference)

- New contract `contracts/src/intents/ZhggEntryPoint.sol` — minimised single-intent
  EntryPoint.
- New standard contracts `contracts/src/intents/standards/SimpleSwapStandard.sol`,
  `RecurringSwapStandard.sol`, etc. Each implements `validateIntentSegment` +
  `executeIntentSegment` and internally calls `SpendCap.consume`, `FeeSplitter.split`,
  the underlying Uniswap V4 router.
- Modify `contracts/src/AgentReceiverWallet.sol` to add `validateUserIntent` (delegating
  to existing 1271 path) and `generalizedIntentDelegateCall` gated by
  `verifyExecutingIntentSegmentForStandard`. ~60 LoC addition.
- Modify `contracts/src/AxiomCommit.sol` — keep it, but key off
  `keccak(abi.encode(UserIntent))` so the commit hash *is* the canonical 7521 intent
  hash. AxiomCommit becomes the audit log for the 7521 envelope rather than a separate
  plan format.
- Modify `apps/demo/src/cross-agent.ts` — between the `audit.axiom.commit` and
  `payment.settle` steps, insert an `intent.solve` step that builds the `UserIntent`,
  calls `EntryPoint.handleIntents`, emits `intent.executed`.
- Modify `packages/workflow/src/*` — add `buildUserIntent()` / `submitIntentSolution()`
  helpers next to `verifyPayment` / `settlePayment`.
- Modify the planned `packages/sdk/src/intents/_types.ts` IntentDef — add
  `standardId: bytes32` so each zhgg intent file maps 1:1 to an on-chain `IntentStandard`
  address.

## Risks / footguns

- **Spec is a stale Draft.** Adopting today means betting on a standard the authors
  haven't pushed in two years. Any change to revision 2 forces a redeploy of the
  EntryPoint and re-registration of every standard.
- **Singleton EntryPoint = central trust point** the spec itself calls out as needing
  "very heavy auditing and formal verification". Hackathon project — no audit budget.
- **No solver mempool exists for 7521.** You'd be the only solver. The whole MEV/solver
  story is hypothetical.
- **Per-chain redeploy.** Standard IDs are scoped to (intent standard contract, entry
  point contract, chainId) — register every standard separately on 0G Galileo (16602)
  and Base Sepolia (84532), and lose intent-hash equality across chains.
- **Replay defence is *not* in the entry point.** Spec explicitly says "updates to state
  for things like nonce management, should be done in an individual segment". You
  re-implement nonces inside every `IntentStandard`. Easy to get wrong.
- **MEV exposure.** Once `UserIntent`s are public, solvers can sandwich any swap intent.
  UniswapX-style RFQ mitigates this; 7521 vanilla does not.
- **Loss of orchestrator flexibility.** Today `cross-agent.ts` can interleave 0G
  inference, ENS, x402, and audit posts in arbitrary order. Forcing the same flow through
  `handleIntents` straitjackets the orchestrator into the 7521 verification→execution
  loop.
- **ERC-1271 + 7521 interaction is under-specified** — the receiver wallet's
  `validateUserIntent` would have to coexist with the existing public-trigger /
  iNFT-owner-following logic in `AgentReceiverWallet.sol`. Non-trivial.

## Alternatives

- **ERC-7683 (cross-chain intents)** — Draft but vastly more adopted. erc7683.org, Open
  Intents Framework with Arbitrum/Optimism/Scroll/Polygon, Across as canonical filler.
  Defines `GaslessCrossChainOrder` / `OnchainCrossChainOrder` and a `Settler` interface.
  *Better* fit than 7521 if zhgg ever wants cross-chain solver fulfilment for swap-style
  intents — but still overkill for the agent-pays-agent loop.
- **UniswapX-style off-chain intent + Permit2 + Reactor** — battle-tested, no entry-point
  standard, just an order format and a single executor contract. Closer in spirit to what
  zhgg already does with `AxiomCommit` + `AgentReceiverWallet`.
- **CoW Protocol intents** — production-grade, off-chain solver auction, on-chain
  settlement.
- **Anoma intents** — research-stage, full intent-centric L1; not relevant for an EVM
  hackathon project.
- **Status quo: zhgg's own Zod registry + AxiomCommit + ERC-1271 + x402.** Already covers
  intent envelope (Zod schema → JSON → keccak → AxiomCommit), authorisation (1271 sig on
  AgentReceiverWallet), settlement (x402 / FeeSplitter), audit (0G Storage Log + 8021
  suffix).

## What to build instead

1. **Treat the existing Zod intent registry as zhgg's intent layer.**
   `packages/sdk/src/intents/_types.ts` + `_registry.ts` (described in `CLAUDE.md`) is
   your `IntentStandard` analogue — keep it off-chain, version it, let the planner read
   from it.
2. **Promote `AxiomCommit` to the canonical intent-hash anchor.** Define stable
   canonical-JSON serialisation in `packages/workflow/src/canonicalIntent.ts`, hash it to
   `bytes32`, commit via `AxiomCommit.commitPlan`, reveal post-receipt. This *is* zhgg's
   "UserIntent" without the 7521 entry-point baggage. Update `apps/demo/src/cross-agent.ts`
   to emit an `intent.canonical` event with the canonicalised body alongside the existing
   `audit.axiom.commit`.
3. **Build the solver as a TS service in `packages/router/`** that consumes registry
   intents, calls MCP tools (Uniswap V4 `swap`/`quote`, ENS `resolve`, `read.balance`),
   wraps execution in `SpendCap.consume` + `FeeSplitter.split` (or x402 for HTTP-mediated
   calls), and emits `intent.solved` to the orchestrator. No new contracts.

If zhgg ever needs a *standardised* on-chain intent format for cross-chain reach, swap in
ERC-7683 — not 7521.
