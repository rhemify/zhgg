# EIP-8004 — Trustless Agents

## Status
Draft — Standards Track / ERC. Created 2025-08-13. Requires EIP-155, EIP-712, ERC-721, ERC-1271. Co-authors: Marco De Rossi (@MarcoMetaMask), Davide Crapis (@dcrapis, Ethereum Foundation), Jordan Ellis (Google), Erik Reppel (Coinbase). Live on Ethereum mainnet 2026-01-29; Base mainnet shortly after.

## TL;DR
EIP-8004 is the trust layer on top of A2A/MCP: three on-chain registries (Identity, Reputation, Validation) that let any client discover, choose, and verify an agent across organizational boundaries with no pre-existing trust. It solves the "who is this agent and should I believe its claims" problem that pure A2A/MCP leave open. By 2026 it is table stakes — every serious agent ships an 8004 identity and posts receipts to 8004 Reputation so reputation accrues to the agent rather than to any single host.

## The Three Registries
- Identity Registry — ERC-721 (URIStorage) NFT per agent. `tokenId == agentId`, `tokenURI == agentURI` resolves to a JSON registration file. Per-chain singleton; cross-chain global ID is `eip155:{chainId}:{registry}` + `agentId`.
- Reputation Registry — clients post signed feedback (`int128` value, `uint8` decimals, two tags, optional off-chain JSON + keccak256 hash). On-chain composable, off-chain rich.
- Validation Registry — agents request, validators respond. `response` is `uint8` 0-100 (binary or graded). Backing mechanism (stake / zkML / TEE) is out of scope.

## State Machine
- Identity: `Unregistered → register() → Active → setAgentURI()/setMetadata()* → transferFrom() (owner change, agentWallet auto-cleared) → burn (optional)`.
- Reputation: `Active agent → giveFeedback() (append-only loop, feedbackIndex++) → revokeFeedback() (sets isRevoked, never deletes) → appendResponse()* (anyone)`.
- Validation: `validationRequest(requestHash) → Pending → validationResponse(requestHash, 0..100) (callable multiple times for soft/hard finality via tag)`.

## Receipt Structure (Reputation feedback)
- `agentId` (uint256) — references Identity Registry token.
- `clientAddress` (msg.sender) — must NOT be agent owner or operator.
- `feedbackIndex` (uint64) — 1-indexed counter per (agent, client).
- `value` (int128) + `valueDecimals` (uint8, 0-18) — fixed-point signed score.
- `tag1`, `tag2` (string) — free-form (e.g. `starred`, `successRate`, `tradingYield`).
- `endpoint`, `feedbackURI`, `feedbackHash` (keccak256 of off-chain JSON; optional for IPFS) — emitted only, not stored.
- Off-chain JSON: `agentRegistry`, `agentId`, `clientAddress`, `createdAt`, `value`, `valueDecimals`, optional `mcp`/`a2a`/`oasf`/`proofOfPayment` blocks.
- Integrity comes from `keccak256(content) == feedbackHash`; authenticity from `msg.sender`. No issuer signature is stored on-chain — the tx itself is the signature.

## Cross-Platform Implications
The registry is a per-chain singleton; the `agentId` is global via `{namespace}:{chainId}:{registry}:{id}`. Receipts live on-chain, off-chain JSON lives on IPFS. Any 8004-aware viewer (Etherscan, marketplace, audit explorer) reads the same data — no platform owns the agent's history. Browsable as plain ERC-721 in any NFT app.

## Coupling with ERC-7857 (iNFT)
- ERC-7857 iNFT = the agent's body (model weights/state via TEE-encrypted metadata). EIP-8004 = the agent's passport (identity + receipts).
- The iNFT `(contract, tokenId)` is registered as an 8004 agent by minting an Identity Registry NFT whose `agentURI` references the iNFT. Reputation accrues to the 8004 `agentId`; ownership/state is governed by 7857.
- When the 7857 iNFT transfers (re-encrypt to new owner), the 8004 NFT can transfer in the same flow — `agentWallet` clears and must be re-proven.

## Coupling with ENS
- An agent's ENS name (e.g. `audit.zhgg.eth`) goes in the registration file under `services[].name == "ENS"`. ENS is the human-readable face; 8004 is the verifiable passport.
- Reverse: an ENS resolver text record can pin the canonical 8004 entry (`eip155:1:0x8004A169...:agentId`) so wallets resolve `audit.zhgg.eth` → 8004 passport → portable receipts.

## Security Considerations
- Sybil resistance: anyone can `register()` and anyone can `giveFeedback()`. The protocol does not police identities — it standardizes signals so off-chain reputation systems (filtered by `clientAddresses`) can score reviewers. `getSummary()` REQUIRES non-empty `clientAddresses` for this reason.
- Receipt forgery: `keccak256(off-chain) == feedbackHash` enforces integrity; tx-level `msg.sender` enforces authenticity. Owners/operators MUST NOT self-feedback (rejected on-chain).
- Stale identity: NFT transfers automatically clear `agentWallet`; new owner must re-prove via EIP-712 / ERC-1271 signature with deadline. Revoked feedback flips `isRevoked` but is never deleted (audit trail integrity).
- Capability claims: 8004 cannot guarantee advertised endpoints are functional or non-malicious — the three trust models (reputation, validation, TEE attestation) cover that gap.
- Validator incentives / slashing are out of scope; managed by the validation protocol.

## How zhgg Uses It
- `audit.zhgg.eth` is registered in the Identity Registry on 0G Galileo (via our adapter) and on Base Sepolia (via canonical contract). Same passport, two chains.
- Every audit job emits a Reputation Registry receipt: `tag1="auditPass"`, `value` ∈ {0,100}, `feedbackURI` → IPFS-pinned audit JSON (findings, gas, slither output), `feedbackHash` enforces integrity.
- High-stake audits use the Validation Registry: a TEE-backed validator re-runs slither/foundry tests and posts `validationResponse(requestHash, 0..100)`. Soft-finality on first pass, hard-finality after 24h challenge window (encoded in `tag`).
- Judges and downstream agents verify `audit.zhgg.eth`'s reputation in any 8004-aware viewer — receipts are not tied to our DB or our UI.
